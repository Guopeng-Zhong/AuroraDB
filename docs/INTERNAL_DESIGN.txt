AuroraDB 存储实现与正确性说明
版本：1.0；核对依据：auroradb/storage.py、auroradb/engine.py

1. 实现边界与文件组织

系统运行时只使用 Python 标准库。查询、堆文件、B+ 树、页缓存、事务日志
均由本项目实现，没有调用 SQLite、MySQL 或其他现成数据库引擎。差分测试
中的 SQLite 仅用于生成对照结果，不参与运行时数据存取。

数据库目录有三个内部文件：
  pages.dat   固定大小页文件，页 p 位于字节偏移 p * 4096。
  redo.wal    单个事务的完整页镜像重做日志；正常提交后清空。
  writer.lock 操作系统独占锁的载体，文件保持存在；进程退出时锁自动释放。

Windows 使用 msvcrt.locking，POSIX 使用 flock。一个目录同时只允许一个
打开的写者连接。Database 的 RLock 串行化同一连接上的 API 调用。
该实现没有并发事务、MVCC 或跨进程并发读者协议。

2. 4096 字节页格式

所有整数头字段采用小端编码，结构为 struct '<8sIII'：

  偏移  长度  含义
  0       8   固定魔数 AURPAGE1
  8       4   无符号页号，须与物理偏移推导的页号相同
  12      4   UTF-8 JSON 有效字节数
  16      4   CRC32 校验值
  20   4076   JSON 内容与零填充

CRC32 输入为 '<II' 编码的页号和有效长度，再连接全部 4076 字节页体。
因此内容、有效长度、页号与尾部填充的损坏都能被检查。魔数另行精确检查。
JSON 使用紧凑分隔符、UTF-8 与确定的对象键排序，拒绝 NaN 和 Infinity。
解码后的页必须是 JSON 对象。读取损坏页返回 StorageError，不自动覆盖。
CRC 用于检测非恶意数据损坏，不是密码学签名。

3. 缓冲池与事务暂存

已提交页位于 OrderedDict 管理的 LRU 缓存。命中时移至最近使用端，缓存
超过 cache_size 时只淘汰最久未用的已提交页。读取和写入都复制对象，避免
调用者修改 Python 字典时绕过 write_page。

事务修改保存在独立的 _staged 字典中。read_page 优先读取暂存版本，实现
read-your-writes；任何暂存页都不会因 LRU 淘汰而提前写入 pages.dat。
分配新页只增长本事务的临时页号；ROLLBACK 丢弃暂存版本并恢复分配边界。
堆表与索引元数据由 Database 的目录快照配合恢复。

该策略是 NO-STEAL。提交返回前还会同步数据页，因此正常确认路径采用
FORCE，同时保留完整页镜像 WAL，处理提交中途写了一部分页的崩溃。
LRU 容量只限制已提交页缓存，事务写集需要额外内存，并未伪称整个进程
只使用 cache_size * 4096 字节。

可观测指标包括 cache_hits、cache_misses、disk_reads、disk_writes、
cache_evictions、cache_used、staged_pages、wal_recoveries 和 poisoned。
disk_reads 统计应用层读页次数，不等同于操作系统实际设备读取次数。

4. WAL 的二进制格式

文件魔数为 8 字节 AURWAL1\0。其后每个记录的帧头是 '<II'：
  uint32 记录体长度
  uint32 记录体 CRC32
  bytes  记录体

记录体有三种类型：
  B：1 字节类型 + '<QQI'：提交前页数、目标页数、页镜像数量。
  P：1 字节类型 + '<Q' 页号 + 完整 4096 字节页镜像。
  C：1 字节类型 + '<QI' 目标页数、镜像数量 + 32 字节 SHA-256 摘要。

摘要按顺序覆盖 B 和所有 P 记录的完整记录体。恢复时检查每帧 CRC、每个
页镜像的页 CRC、页号范围与唯一性、BEGIN/COMMIT 目标和数量一致性、
新分配页全部存在，以及 SHA-256 完整事务摘要。没有正确的终结 C 记录
就不执行任何页镜像。完整记录 CRC 损坏，或可识别完整提交之后的前缀
损坏，会报错并保留原始文件；不会把损坏记录悄悄当作成功事务。

该日志格式只包含一个事务。遇到完整 C 帧之后的任何字节，包括半帧头、
半帧体、CRC 错误帧、未知类型及额外合法 B/P/C 帧，均拒绝恢复并保留
WAL 与数据文件。另行扫描全文件中的完整、长度正确且 CRC 合法的 C 帧；
若 C 帧长度头损坏但固定长度提交体和紧邻 CRC 仍完整，也保留该提交证据。
若有效 B 帧后的全部声明 P 页已经完整而其后出现非空尾帧，即使提交类型字节
也损坏，同样保守拒绝清理。这样前缀魔数/帧长破坏、提交头体损坏 + 异常尾字节
不会被误判为可丢弃的未完成日志。这些证据扫描只用于保守拒绝，绝不单独授权
重做；重做仍须完整通过全部页镜像、数量、目标边界和事务 SHA-256 校验。
完整且 CRC 正确但类型未知的尾帧也属于上述证据，不能因解析游标已经到达
EOF 而误清日志；判断边界使用合法 B/P 前缀的结束位置，并保留两文件原字节。

正常事务含 N 个不同页镜像时，WAL 大小为 90 + 4113 * N 字节。
这是物理页镜像重做，不是 SQL 字符串重放，也不是完整 ARIES 协议。

5. 提交流程与恢复不变量

提交顺序：
  1. 验证全部暂存页可编码，并按页号生成最终镜像。
  2. 写 B、全部 P、C 到 redo.wal。
  3. fsync WAL。此前不修改任何数据页。
  4. 把最终镜像写入 pages.dat，调整文件到目标页数。
  5. fsync 数据文件。
  6. 发布缓存与已提交页数，然后截断并同步 WAL。

第 3 步完成后日志已经足以恢复整个事务。如果第 4 步中途崩溃，启动时
会重新写入全部镜像，既修复覆盖页，也补全附加页；重复重做是幂等的。
如果步骤 2 中途退出，数据文件没有被改动，未完成日志可丢弃。
步骤 5 完成后 WAL 清理失败不会报告虚假的回滚：数据已经持久化，残留
日志再次重做也安全。成功提交后 WAL 通常为空，因而每次提交实际上完成
一次同步检查点；CHECKPOINT 语句不需要后台刷脏页。

提交写日志、写数据或持久化后的缓存发布发生异常时，pager 被标记 poisoned。
这包含复制缓存页引起的 MemoryError；提交结果发布也位于同一个异常保护
边界内，包括暂存清理、事务标志、提交计数和最终 WAL 清理。最终清理的
OSError 仍按数据已持久化的成功处理，其他异常必须 poison，避免 SQL 层
恢复旧目录后继续使用同一连接。在发布完成前不会清空完整 WAL。
KeyboardInterrupt/SystemExit
保留其控制流语义，同时标记 poisoned，防止中断后继续使用不确定状态。
普通读写和新的
事务被拒绝；Database 也拒绝 SQL 执行和 schema()，只允许诊断 stats()
与 close()。内存回滚不会清空可能已经提交的 WAL。关闭后重新打开，才能
确定持久化状态，避免把已经写入日志的事务对用户描述成确定回滚。

这些保证依赖操作系统 fsync 和文件系统按约定工作。进程崩溃测试证明指定
软件故障边界下的行为，不能代替存储硬件断电与控制器故障认证。

6. 多页系统目录

物理页 0 保存 manifest：
  {"kind":"catalog_root","version":1,"pages":[catalog_page_id,...]}

每个目录分片是：
  {"kind":"catalog_chunk","ordinal":0,"data":"base64-encoded-bytes"}

逻辑目录使用 UTF-8 JSON，按原始字节每 2900 字节切分并分别 Base64 编码。
启动按照 ordinal 验证并拼接、解码后恢复完整逻辑目录：
  {"kind":"catalog","version":1,"tables":{table_name:table_meta,...}}

这样 75 张表的目录也能跨多个页保存，不受单个 JSON 页 4076 字节限制。
修改目录的全部分片、manifest、堆页和索引页处于同一个页镜像事务中。
根索引页号变化、row_count、heap.pages 与行数据具有相同提交边界。
旧版直接放在页 0 的逻辑目录可以读取，下一次写入会原子迁移到分片形式。

manifest 本身仍需放入一个页，因此目录分片数量依然有有限上界；具体值
取决于分片页号的十进制长度。目录缩小时空闲分片可能被当前连接复用；
没有可达引用的分片不会自动回收。该版本没有目录压缩和页回收器。

7. 堆文件与稳定 RID

表元数据记录 columns、pages、next_rid、row_count 与 indexes。
可选的 insert_hint 指向当前追加页，reusable_pages 记录有删除空槽的页；
二者与表元数据一起事务化保存。普通追加只检查追加页，避免每次插入遍历
之前所有已满页。插入优先检查有删除空槽的页；大行放不下的空槽仍会保留
给后续小行。在一个 HeapTable 操作对象内，还用可用字节数过滤无望候选页。
旧格式元数据第一次修改时扫描一次堆页，建立这些提示。一般追加的页读取
随行数线性增长；大量不同宽度空槽的匹配仍可能需要检查多个候选页。
先前满页剩余的零碎空间和缩小更新释放的空间不会做全局最佳适配，因此
实现接受一定的内部碎片，避免通过无界全表扫描寻找极小空余。
堆页为 {"kind":"heap","rows":[{"v":values_dict},null,...]}。
逻辑槽号是 rows 数组下标，不是运行时 Python 地址。RID 为 JSON 数组
[heap_page_id, slot_id]，可跨重启保存，用于 B+ 树回表。

删除把槽设为 null；不会移动其他槽，所以其他记录 RID 保持不变。插入
可复用删除留下的槽。next_rid 是兼容元数据计数，实际定位依据是 RID。
同一个槽被删除后再次插入，旧 RID 可以指向新记录；不能把 RID 当成永不
复用的业务主键。

更新先尝试把新内容写回原堆页。若记录本身可存储，但所在页空间不足，
则把内容置于 {"kind":"overflow","values":values_dict} 页，把原槽改为
{"overflow":overflow_page_id}。这样即使数据增长，原 RID 与索引引用也
不变。再次增长可重写已存在的 overflow 页；缩小后可以移回原槽。
旧溢出页可能变为不可达页，当前版本保留它。

单行必须可以装进一个空堆页；整条行的 UTF-8 JSON 含结构开销须在页体
容量内。大于该限制的行会在修改前被拒绝，不提供任意长度 LOB 链。

8. B+ 树页、重复键与范围扫描

叶节点：
  {"kind":"bplus_leaf","entries":[[key,[heap_page,slot]],...],"next":id_or_null}
内部节点：
  {"kind":"bplus_internal","keys":[[key,[heap_page,slot]],...],"children":[id,...]}

键顺序先比较 SQL 值，再比较 RID 中的页号、槽号。数值/布尔类和文本类
有确定的类型顺序；正常表索引由列类型约束，使用一致的类型。NULL 不进入
索引，唯一约束允许多个 NULL。相同 key 的不同 RID 可以跨多个叶节点；
同一个 (key,RID) 再次插入是幂等操作。

内部节点的 children 数量始终为 keys 数量加一。separator 是右子树的
下界 fence，下降时使用 bisect_right；叶内部使用有序插入。叶溢出按
编码字节平衡分裂并维护 next 链，复制右叶最小复合键到父节点。内部页
溢出时把中间 separator 提升到父节点。根分裂分配新的内部根，并立即
更新传入的 index_meta['root']，使系统目录能原子持久化新根。

等值扫描从 (key,[-1,-1]) 定位最左可能叶，再顺着 next 读取全部重复键。
范围扫描只需一次树下降，然后按 next 遍历，支持开闭边界和无界端点。
返回的 RID 随后经过堆文件获取真实行，执行器还会检查完整 WHERE 条件。

删除采用延迟合并策略：只移除叶条目，保留现有 fence 与空叶。不维持
传统删除后的半满占用率约束，但保留严格顺序、范围 fence、各叶等深和
叶链完整性。删除过多后访问性能会退化，需要未来的合并或重建功能。
validate() 检查这些实际维护的不变量，并返回 pages/leaves/height/entries。

单键的 UTF-8 JSON 编码最大 1024 字节。键长度限制保证叶和内部 separator
可以分裂到合法页，不是按字符数限制。oversize key、非法 RID、非有限数
会在写入前报 StorageError。

9. 与 SQL 层的原子性配合

写语句没有显式事务时自动开始并提交；BEGIN/COMMIT/ROLLBACK 管理显式
事务。Database 开始事务时保存逻辑目录与目录分片页号列表的深拷贝。
失败写入丢弃全部暂存页并恢复快照，即使错误发生在索引旧条目移除之后，
也不会留下丢失索引或半更新堆行。所有 UPDATE 目标先快照，再进行写入，
避免修改过程中重复遇到同一条目标记录。

SQL 去重与分组使用带类型的 row_signature，区分 BOOLEAN 与数值 0/1，
同时保留 INTEGER/REAL 的数值兼容。JOIN 的已知比较类型在选择哈希连接或
嵌套循环前检查，不让物理算法或空输入掩盖不兼容类型；动态类型表达式在
执行时继续校验。NULL 仍按项目的 SQL 三值逻辑处理。

测试证据在 tests/test_storage.py 和 tests/test_integration_storage.py：
  - 真正子进程 os._exit 的日志前缀、WAL 同步后、部分数据写后故障边界。
  - 完整日志修复残缺附加页、坏日志保留、全部页区域 CRC、操作系统锁。
  - 提交已 fsync 后缓存发布 MemoryError 的 pager/Database 回归及恢复。
  - 已发布暂存/事务状态后的 WAL 清理 MemoryError 回归，防止旧目录继续使用。
  - 提交中的 KeyboardInterrupt 保留语义，但禁止继续读取不确定状态。
  - 8 种异常 WAL 尾部，以及魔数/BEGIN 帧长/PAGE 帧长损坏并带尾部、
    C 帧长度损坏（含 C 类型字节同时损坏）且部分数据已落盘的回归；
    均验证拒绝时日志与数据原字节保留，恢复有效日志后才能完成重做。
  - 合法 B/P 前缀之后的完整未知帧被消费到 EOF 时，仍拒绝清理和恢复。
  - 2200 随机重复键的等值/范围/删除/重启；1000 完全相同键跨叶扫描。
  - 大文本键形成多层树；唯一键、NULL、oversize key 和 row 的边界。
  - 增长更新通过 forwarding 保持 RID，索引和堆数据重启后相互一致。
  - 1000 行追加的读页次数上界，以及大小行交替情况下的删除空槽复用。
  - 75 张表的多页目录、显式回滚、旧目录迁移、提交异常的拒绝读取。
  - catalog/heap/index 的真实进程崩溃后全有或全无恢复。
